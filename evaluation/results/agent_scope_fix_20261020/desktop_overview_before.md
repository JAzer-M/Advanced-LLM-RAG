## 1. 项目目标与当前结论

### 1.1 我们最终要做什么

做一个可解释、可复现、能够引用论文原文的科研问答系统，并逐步发展为有工具调用能力的 Agentic RAG。最终应能展示：

- 给定问题，能从论文中找到证据，说明来源和页码，再组织答案。
- 首轮证据不够时，能指出具体缺什么，选择定向检索或邻段读取，而不是机械增加上下文。
- 没有资料、条件不匹配或预算耗尽时，能有依据地停止、部分回答或拒答。
- 能用固定 RAG 与 Agent 的同条件对照说明收益、失败、额外调用和成本。
- 能作为大模型应用、RAG、Agent 开发实习项目讲清楚；目前尚未绑定具体岗位 JD。

项目不包含 Fine-tuning、LoRA、QLoRA，也不与另一个 PyTorch Transformer 架构项目混在一起。主线不以采购 GPU、训练模型或下载大量论文作为前置条件。

### 1.3 “本地最小 Agent”是什么意思

程序控制、工具、向量检索、重排、知识库和日志在本机；规划、证据检查及生成可调用现有模型 API。因此它是本地运行的应用，不是所有模型推理都离线。

第一版只需要一个 Agent：使用普通函数、字典和列表，把状态、动作和停止条件写清楚。没有已出现的复杂需求时，不增加多 Agent、通用插件框架或分布式系统。

### 2.2 从现在到完整本地 Agent，还剩多少步骤

为方便后续执行，本总览将剩余 P2 工作整理为五个工作包。以下细分编号是路线整理，不表示这些工作已经执行，也不是新的付费实验授权。

| 顺序 | 工作包 | 验收时要看到什么 |
| --- | --- | --- |
| 1 | P2.1 收紧已实现的需求／证据检查 | h10 不再扩大数据集范围；训练目标不再被当作评测判据的 partial 支持；原来正常的两题不退步 |
| 2 | P2.2 接入最小本地工具 | search／read_neighbors 能真正返回可定位原文、失败状态和调用记录 |
| 3 | P2.3 实现有预算的执行闭环 | 执行建议后更新证据、重新检查；能因充分、无进展、缺资料、错误或耗尽预算停止 |
| 4 | P2.4 生成并检查最终答案 | 对需求逐项交代已答／部分／缺失，检查主体、数值、条件和引用，而非只看编号 |

也就是说：**完整本地 Agent 主线还有五个工作包，其中第一个是当前第一步的语义修正。** 若继续完成后续展示路线，再加 P3 联网、P4 界面／必要编排、P4 复现／材料三个工作包，共八个。工作包不是 API 调用次数，也不代表每包都只需要一轮修改。

原计划中更大题集、虚构文档证据实验、稳定跨版本 ID、通用增量导入仍是可选增强，不全部强行塞到当前最小主线。

## 3. 从最初到现在的历史路线

本节按先后解释做过什么、得到什么、为什么改变方向。早期数字为历史记录，本次没有在 Mac 上重跑那些旧配置。不同分块、Gold、题集、语言、K、语料和选择策略的分数不能直接相减归因。

### H01：最小本地 RAG 与三篇原始论文

最初语料是 Transformer、DCNN／AlexNet、VGG 三篇，共 32 页，没有 ResNet。先完成 PDF 读取、分块、MiniLM 向量化、FAISS 检索，再把检索原文交给模型生成。

这一阶段建立了最基本的数据链路，也发现“答案说得流畅”不能说明检索到了依据。后续因此分别检查候选召回、最终上下文、生成理解和引用。

### H02：2026-10-14，三种分块 × 四种检索

历史 Parser V1 下，Fixed／Recursive／Semantic 为 340／340／385 块；使用 384 维 MiniLM，五道可答题，每路 Top-20、最终 Top-5，重排模型为 `cross-encoder/ms-marco-MiniLM-L6-v2`。

- Fixed + Hybrid + 重排：Recall@5 = 0.7167。
- Recursive + Hybrid + 重排：Recall@5 = 0.6167。
- Semantic + Hybrid + 重排：Recall@5 = 0.6633。

当时按较高 Recall 阶段性选择 Fixed 方案，但没有一种方法在所有指标都最优。Fixed 和 Recursive 即使块数相同，正文也并不相同，不能互换索引和 JSON。

### H03：2026-10-15，BGE、查询增强与早期 Gold 整理

更换为 `BAAI/bge-reranker-base` 后，历史 Semantic + Hybrid + BGE 的 P@5／R@5／MAP／MRR 为 0.4000／0.6900／0.4119／0.5800。后续固定 Semantic + BGE 做查询优化对照，便于控制变量，不宣称它是所有配置中的绝对最优。

做过 Original、Rewritten、Multi-Query 等查询实验。部分改写改善了中间 Dense 结果，却没有改变最终重排后的 Top-5。因此后续坚持检查最终真正送入模型的证据，不能只凭辅助查询更丰富就声称有效。

早期也修复过“标为 Original 的基线实际用了改写查询”和重复调用改写的问题。Gold 曾补充小卷积核、数据增强证据，补充前后指标不能当作同一数据集的公平提升。

历史 VGG 失败还说明：关键段落可能在 BM25 中出现，却被 RRF 截断或 BGE 降序丢掉；扩展邻段又会带来表格和邻近主题噪声。即使人工给予正确 Gold 原文，本地生成也曾把三层 3×3 感受野说错。由此确认检索和生成需要分开诊断。

历史分块数量 330／331／403、340／340／385 属于不同中间版本；当前 Mac 三篇 Semantic 库为 378 块。不能把这些数字视为同一资产，或把旧 Gold ID 直接用于现库。详细旧表见[历史实验记录](/Users/j/Desktop/Advanced-LLM-RAG/docs/experiments.md)。

### H04：2026-10-18，API 主流程与本地 Qwen 对照

调通过 API 生成，保留分解、检索、证据账本、最终回答和引用检查。另选三道旧题集以外的问题，固定相同提示、相同原文，比较本地 Qwen3.5-2B 与 API 最终生成；双方输出上限为 512 token。

三题预设要点评分为 Qwen 8.5/12、DeepSeek 11.5/12。API 对照减少了当时的目标移位／掩码、重叠池化分类等明确错误。但这只是三题人工开发性评分，不能写成总体准确率提升 25%，也不是两套完整系统端到端比较。

同三题运行 base／rewrite／HyDE／both：rewrite 和 both 最终 Top-10 均与 base 相同；HyDE 只替换一题第十条，没有补到核心缺证据。默认继续关闭两个增强。HyDE 生成的假设文字只用于检索，不能作为论文事实证据。

同时修正数学区间 `[256; 512]` 被误认为引用的问题，避免无必要修复。记录了 VGG 固定裁剪证据缺失等边界；模型换强不能替代证据覆盖检查。

## 6. 离线流程：论文怎样变成可检索知识库

完整离线路线是：

```text
明确知识需求／论文清单
  → 获取固定版本 PDF 和来源信息
  → 校验文件，记录成功／失败／跳过
  → PDF 解析与文本质量抽查
  → Semantic 分块，保留来源和页码
  → MiniLM 编码、归一化
  → FAISS 索引 + chunks + manifest
  → 成对校验，发布新版本
  → 按需要显式选择／激活，旧版本继续保留
```

### 6.1 选论文与获取

先根据问题覆盖选择论文，当前五篇已覆盖生成式检索、双编码器、交互式检索、自反思和纠错检索等知识主题。不是为了提高库大小盲目下载。

目前已实现固定 ID／版本清单的下载。未来若接论文元数据 API，可把“手工确定候选”扩为主题查询、作者／时间筛选、摘要筛选、追踪版本和来源；API 不会自动判断所有论文都值得入库，也不等于全部正文均可获得。

### 6.2 解析与分块

读取正文、页码、标题等信息，再按现有 Semantic 方法分块，构建时使用 `max_chunk_size=500` 字符、`percentile=10`。单个超长句不硬切，但短句／短片段过滤、跨页断句和复杂版式会造成信息损失，不保证每块不超 500 或解析无损。

每块保留 `chunk_id`、`text`、`source`、`page`、`title`、`section`。双栏文件有显式处理条件；公式、整表和跨页句子还不可靠。检查“PDF 下载成功”和“关键内容解析成功”必须分开。

### 6.3 编码、索引与版本发布

正文经 MiniLM 得到 384 维向量并归一化，放入 FAISS `IndexFlatIP`。标题保留为元数据，并用于后面的 BGE／生成；不能据此说标题已经进入当前 Embedding 或 BM25 的正文索引。

先写新版本临时目录，通过数量、维度、ID、哈希等检查后发布；不覆盖旧版。激活是独立动作，不能把“新库构建成功”当作“默认库已经切换”。

### 6.4 离线产物如何验收

1. 文件与论文版本、来源、页数对应，下载失败与解析失败分别记录。
2. 抽查关键原句、页码、片段顺序以及表格／公式等高风险内容。
3. 索引向量数与 chunks 数一致，manifest 哈希、维度、ID 对应通过。
4. 同批重复导入／下载不产生无意重复，旧版本仍可定位。
5. 有需要时在新库运行代表性检索和旧题回归；不以下载数量作为质量指标。

## 7. 固定 RAG 的完整问答流程

这里描述已经实现的 `main.py`。它包含有限规则补查；与第 9 节的需求驱动 Agent 分开理解。

```text
用户问题 + 固定知识库版本
  → API 判断是否分解，必要时生成 2～4 个子题
  → 原问题 Dense + BM25 → RRF，保存原问题锚点
  → 可选 rewrite／HyDE（现关闭）和子题检索
  → 合并、去重
  → 原问题全局 BGE + 子题局部排序
  → Top-10 预算内选择、保护关键线索
  → 按来源覆盖信号最多两轮定向补查
  → 原文 + 标题 + 规则证据账本
  → API 最终答案
  → 引用结构检查，必要时最多一次修复
  → 保存答案、上下文、来源、调用和失败状态
```

### 7.1 每一步解决什么问题

| 步骤 | 输入 → 输出 | 作用与边界 |
| --- | --- | --- |
| 1. 固定库与问题 | 问题、显式版本或激活指针 → 本次库 | 保证索引、正文、Gold 和日志可追溯 |
| 2. 分解判断 | 原问题 → 是否拆分、有效子题 | 比较题可按主体／维度拆；子题不得增加原题没有的前提；h10 说明仍会范围漂移 |
| 3. Dense | 查询向量 → 语义候选 | 有利于语义近似，不保证数值或特定术语准确命中 |
| 4. BM25 | 英文／数字词项 → 关键词候选 | 与 Dense 互补；无有效词项返回空，零分过滤；中文词法能力尚未完善 |
| 5. RRF | 多路排名 → 融合候选 | 以名次合并，原问题第一条锚点在增强前确定 |
| 6. 子题／可选增强检索 | 子题、改写或假设文档 → 更多候选 | 现行使用分解，rewrite／HyDE 关闭；假设文档不充当事实 |
| 7. 去重与 BGE | 候选、问题／子题 → 全局／局部排序 | 估计相关性；高分不等于足以证明特定事实 |
| 8. 预算内选证据 | 排序、锚点、局部优先 → Top-10 | 避免某个比较对象被挤掉；每个 K 独立选择 |
| 9. 来源补查 | 来源覆盖信号 → 定向候选与再选择 | 有信号才查，至多两轮；按来源覆盖不等于按事实充分性覆盖 |
| 10. 上下文和账本 | 已选原文、元数据、有限规则 → 提示 | 约束主体／数值等，但规则有限，不等于完整语义审查 |
| 11. 最终生成 | 问题、实际上下文 → 带引用答案 | 应根据证据组织答案；仍可能遗漏、过度保留或追加未引用事实 |
| 12. 引用检查与记录 | 答案、引用注册表 → 结构检查／修复记录 | 编号和存在性通过不代表原文支持结论，更不代表主体条件绑定正确 |

### 7.2 固定补查为什么还不等于完整 Agent

当前 main 只对能识别两个以上论文来源且有覆盖信号的问题触发补查；单篇或无信号问题会跳过。每轮最多四个来源任务，第二轮加深同批任务的候选。它没有逐项理解“用户具体需要哪些事实、当前哪一项缺失”。

因此会出现：论文来源都齐了，关键句仍缺失；补查把 Gold 找进候选，却没保留到最终上下文；原文已进上下文，生成仍漏掉细节。P2 的目的就是把这些缺口变成明确状态和可核验行动。

### 7.3 日志里两个证据数量为什么不同

`selected_ids` 是检索选择的 10 条，用于对应检索指标。规则账本可能再附加少量原文锚点，所以 P1 的实际 `citation_registry` 是 10～12 条。评答案和成本时要看完整实际上下文，不能只报 Top-10 而隐藏附加输入。

## 8. 评测、Precision 归一化与目前效果

### 8.1 先把四层问题分开

| 层次 | 要回答的问题 | 主要记录 |
| --- | --- | --- |
| 候选召回 | 需要的原句是否进入 Dense／BM25／融合候选？ | 候选 ID、阶段排名、来源、Gold 映射 |
| 最终证据选择 | 候选中已有的证据有没有进入实际上下文？ | selected_ids、补查前后选择、完整 citation_registry |
| 答案语义 | 已提供的证据是否被完整、正确地表达？缺证据时是否合理停止？ | 冻结核心点、遗漏／部分／错误、拒答和比较条件 |
| 引用与成本 | 关键结论是否由引用支撑？多花了多少资源？ | 结构／存在性／语义分别检查；真实 API 次数、token、耗时、失败 |

检索指标高不保证答案完整；引用编号合法不保证引文支持结论；模型知道一个事实也不等于当前检索提供了该事实。

### 8.2 各指标怎样理解

令某题的最终预算为 K，去重后的指定 Gold 数为 G，前 K 条中命中的不同 Gold 数为 H：

- `Precision@K = H / K`：预算内有多少比例命中了指定 Gold。
- `Recall@K = H / G`：指定 Gold 被覆盖多少；当前报告中的 Recall 通常是逐题平均，即 Macro Recall。
- MAP：先逐题计算 AP，再平均；关注相关证据的覆盖及排名。
- MRR：首个 Gold 命中的倒数排名再平均；只看首个命中，不能替代多证据完整性。
- `nP@K = H / min(K, G)`：已经完成“该题在这个预算内最多可命中的指定 Gold”的多少。

无 Gold 题不参与这些检索分数，另测拒答／边界；无可计分题时 nP 返回 None，而不是人为给 0 或 1。

### 8.3 为什么以前 Precision 很低，甚至难以达到 0.2

Gold 是指定原文片段，通常只有一至几条；最终却检索 10 或 20 条。例如 G=2、K=10，即使两条全命中，原 Precision 也只有 2/10=0.2。若 G=1，上限就是 0.1。不是所有低于 0.2 的值都代表系统完全没找到答案。

旧 42 题累计 81 条 Gold，各题 G≤8。平均 P@10 的可达上限为 `81/(42×10)=0.192857`；P@20 上限为 `81/(42×20)=0.096429`。因此这组题原 P@10 理论上就达不到 0.2。

但也不能据此忽视真实漏召。Gold 不穷尽全部有用段落：未标注片段可能有用、可能等价，也可能是噪声。原 Precision 衡量的是“指定 Gold 命中比例”，不自动等于全部上下文的真实有用比例。

### 8.4 已经实现的归一化口径

逐题的理论最大 Precision 为 `min(K,G)/K`。所以用户提出的做法成立：

```text
逐题 nP = Precision / 该题 Precision 理论上限
        = (H/K) / (min(K,G)/K)
        = H/min(K,G)

报告的整体 nP = 所有可计分题的 H 之和 / 所有 min(K,G) 之和
```

**整体 nP 不是简单平均逐题 nP。** 当所有 G≤K 时，整体 nP 等于 Micro Recall，原报告 Recall 是 Macro Recall，二者权重不同。以后遇到 G>K，nP 的分母截断为 K，不再等于普通 Recall。

报表已直接增加 nP，可按 0～1 或百分比阅读，不必再手算上限。例如旧 42 题 Top-10 的 nP=0.6790 表示完成预算内指定 Gold 可达命中量的 67.90%；不是答案准确率 67.90%。归一化只改变表达，不提升检索，不覆盖语义和引用检查。

### 9.1 为什么第一步不直接执行工具

需要先验证模型能否正确理解“用户要什么”和“当前资料支持到哪一步”。如果它把主体或数据集归属弄错，即使工具接口正确，自动执行仍会朝错误目标检索。第一步因此限定为只输出需求、证据状态与行动建议，并保留可审阅输入。


## 10. P2 后续逐步实施方案

以下全部是待办方案。先把现有失败修清，再逐步增加工具和循环；每步交付代码、最小充分验证及 MD 日志，不在文档整理时自动开始这些实验。

### P2.1：修正需求范围和 partial 判定

**目的：**保证 Agent 查的是用户真正问的事实，不把关系绑定错误传播给工具。

具体做法：

1. 用已保存的 h10 输出定位“原问题 → 需求 → 证据状态 → search 参数”哪一环扩大了主体／数据集／条件范围。
2. 保留原题的完整关系和限定条件，必要时给现有需求字典增加清楚的范围字段；不能只用名字出现、短引出现作为语义通过条件。
3. 约束生成的需求和搜索参数不得凭空给另一主体分配数据集或实验条件，不把原题未要求的逐数据集拆分当作必须需求。
4. 明确 partial 必须确实支持同一需求中的一部分；训练目标与评测判据只有背景关联时，应记为该判据缺失。
5. 先用保存输出和人工构造的简短范围／状态案例做本地验证，再固定小规模真实复核的题目和调用上限；原始失败不覆盖。

**产物：**最小代码／提示约束修改、范围和支持关系回归检查、新旧输出及人工对照 MD。

**完成条件：**h10 的需求及 search 参数不再把 PopQA 分配给原始 RAG；训练损失不再算作判据支持；h01／h11 原来合理的行为不退步。不能只凭改完提示或本地字段校验宣称语义已修好。

### P2.2：让本地工具真正返回可用原文

**目的：**把建议变成可审计、可恢复、可判断成功或失败的工具动作。

具体做法：

1. `search` 复用已有 Dense／BM25／RRF／BGE 和按来源限定能力；先限定论文，再截断结果。
2. `read_neighbors` 按当前库中已知片段读取相邻片段／页面，限制范围，防止数字 ID 跨到另一篇论文。
3. 返回结构统一到少量字典字段：实际查询、来源／页码、chunk ID、正文、库版本、状态和错误；不为此搭通用插件系统。
4. 去重、保存请求和结果；没有命中与工具／服务失败必须分别记录。

**产物：**两个本地工具入口、实际读取示例、错误／边界检查和工具日志。

**完成条件：**返回原文能还原到对应版本；邻段不会跨来源；没有命中时不编造；运行日志能看清用了什么参数、得到了什么。

### P2.3：执行工具 → 更新证据 → 再检查

**目的：**形成真正的最小 Agent 闭环，而不是固定检索后多问模型一次。

建议状态保留：原问题、需求及范围、已获原文、逐项支持状态、缺口／冲突、行动历史、已用预算、停止原因。沿用字典和列表，先实现单 Agent。

流程：

```text
需求规划 + 首轮检索／证据
  → 逐项检查
  → 充分：进入回答
  → 不足且可补：选择并执行本地工具
  → 合并新增原文，重新检查同一组需求
  → 更新行动／预算
  → 回答、部分回答或停止
```

每次检查应基于实际新证据；去重后没有新增有效证据、重复同一查询、来源根本不在本地、预算耗尽或 API／工具失败时停止。只记录简短的行动理由和可见结果，无需冗长内心推理。

实施时预先固定每题 API 次数、工具次数、邻段范围及最多轮数，并保存实际使用量。当前“6 次”仅是上一轮三题诊断的批次上限，不自动成为完整 Agent 每题预算。

**产物：**可中断恢复的执行循环、逐轮轨迹、停止状态和预算记录。

**完成条件：**至少能展示首轮足够不补查、真实漏检后补到证据、没有资料停止、重复无进展停止、工具／API 失败保存。不能用题号或 Gold ID 写死补查。

### P2.4：综合回答与关键结论核对

**目的：**解决“证据已经给了，答案仍漏细节／错条件／没有引用”的问题。

具体做法：

1. 以原问题和最终证据组织答案，逐项交代需求；支持不足时明确部分可答与缺口。
2. 检查主体、数据集、训练／测试阶段、数值、比较条件和结论是否对应原文。
3. 关键事实与实际引用对齐，附带数值也要引用；结构检查仍保留，但另外评语义和完整性。
4. 若允许修订，预先限定次数；修订前后及调用成本都保存，不能无限自我反思。
5. 避免在两篇分别都有证据时，因为没有一段直接比较两篇就拒绝做合理综合。

**产物：**最终答案、需求覆盖表、引用支持核对和有限修订记录。

**完成条件：**有证据的关键点不被悄悄省略；无证据部分不靠常识伪装成有来源；部分回答、资料缺失和服务错误分别表达。语义检查器本身仍需人工抽查，不能用模型一句“通过”代替验收。

### P2.5：与固定 RAG 做质量／成本对照

**目的：**证明闭环在什么情况下有帮助、什么时候不值得多执行。

具体做法：

1. 已知 h 系列用于开发／回归，保留原基线；另冻结新的独立验收题及证据、评分和预算。
2. 固定同一知识库、原问题、生成模型和输入条件；同时公布固定 RAG 与 Agent 的证据／调用预算。
3. 如 Agent 允许更多资源，明确额外资源，并尽可能补一个相近预算的固定策略对照，避免把多查多读算成规划收益。
4. 分别统计最终指定证据覆盖、答案核心点完整性、引用语义、拒答、错误行动、工具次数、API 次数、token、耗时、失败。
5. 保存完整轨迹，挑出两至三个成功／失败案例；扩库或联网属于其他变量，不同时混入本地 Agent 收益。

**产物：**固定 RAG／Agent 表格、独立题集、逐题答案／证据／轨迹、费用与失败说明、MD 结论。

**完成条件：**能复算、能解释收益与退步，知道什么时候应该停止。若收益不稳定，保留固定 RAG 为可靠模式，不因加了 Agent 名称就默认取代基线。

## 11. P3／P4 后续路线

### 11.1 P3：按需联网发现论文并读取正文

触发情形包括用户需要最新资料、本地目录不覆盖目标论文、本地定向检索后仍缺关键原文。先尝试面向论文的发现与正文读取，再按真实需要决定是否引入通用网页搜索。

流程：

1. 明确缺失的是哪篇、哪个事实或哪个时间范围，生成受限搜索请求。
2. 获取候选论文元数据，筛选相关版本和来源，记录 URL／日期／获取时间。
3. 读取可访问正文，保留页码／段落定位；只看到摘要时不能说已读全文。
4. 外部原文先用于本次任务，检查质量、版本和重复后再决定是否进入长期库。
5. 对超时、限流、正文不可访问和预算耗尽保留状态；外部文本作为资料，不作为改变系统行为的指令。
6. 与纯本地模式比较补到了什么、答案是否改善、增加多少调用和延迟。

**完成条件：**可追溯的外部原文确实填补具体缺口，或者清楚说明为何无法获得；不以搜索结果标题和摘要代替细节证据。

这里涉及三类不同 API／服务：

| 类别 | 用途 | 当前进度 |
| --- | --- | --- |
| 生成模型 API | 分解、规划、证据检查、生成答案 | 已使用现有本地私有配置，不必为当前文档再申请 Key |
| 论文元数据／下载入口 | 找论文、按作者／时间筛选、追踪版本、获取正文地址 | 固定版本下载已做；通用发现流程尚未接入 Agent |
| 通用网页搜索 | 查非论文或更广网页资料 | 未选择供应商，未接入 |

直接到 arXiv 手工下载与程序获取可以得到同一 PDF；自动接口的价值是批量筛选、可复现清单、版本／来源记录、重复跳过和故障处理。它不是自动让知识库变聪明，也不是必须先下载海量论文。服务当前价格和限制在真正接入时重新查官方规则，不把旧调研当永久有效。

### 11.2 P4 第一部分：必要编排与演示界面

先保持已验证的普通函数和状态。如果分支、恢复、人工介入或流程展示需求确实增加，再用 LangGraph 表达已稳定流程；采用框架不作为 Agent 成立的必要条件。

**完成条件：**从界面可运行代表性任务，引用能回到原文，失败／部分回答可见；界面展示与保存日志一致。是否另做 HTTP 服务或 Docker 由后续真实展示／岗位需要决定。

### 11.3 P4 第二部分：复现交付和实习材料

整理依赖、启动说明、可公开的论文清单和下载入口、私有配置模板、架构／数据流、固定 RAG／Agent 对照、两至三个失败复盘及真实贡献清单。许可和凭证边界按实际资产处理，不把本地私有配置、模型缓存或无授权全文打包公开。

再写简历与面试讲解：能解释 Dense／BM25 的互补、RRF／BGE 的区别、增强为什么可能无收益、nP 的意义、来源覆盖为什么不等于事实覆盖、Agent 的预算和停止条件。

**完成条件：**他人在说明的环境和依赖下可启动核心 demo；所有简历数字能回指实验；本地成果、已推送代码、可部署服务分清。提交、推送、外部发布按后续明确授权执行。
