## 1. 项目目标与当前阶段

目标：完成一个面向科研论文的 Agentic RAG 应用，能够规划检索、选择工具、检查证据缺口、补充资料、给出可追溯回答，并通过对照评测解释收益与成本，用于实习投递和面试展示。

目前按大模型应用 / RAG / Agent 开发实习方向规划，尚未绑定具体 JD；拿到岗位描述后再调整重点。既要能运行，也要能讲清核心代码、设计取舍、实验口径、失败案例和本人实际理解与贡献。

**已完成：固定流程的 Advanced RAG、API 生成接入、模型与查询增强实验、必要清理。待实现：批量论文导入、自适应 Agent、联网工具、LangGraph 编排与演示界面。**

Single-Agent 可以承担完整的动态规划和工具调用；多 Agent 不是必要条件。“证据不足时最多补检索一次”仅适合作为早期验证步骤，不再作为最终目标。完整 Agent 仍应有可配置的调用、时间和 token 预算，以及明确的停止条件。

## 2. 当前真实流程

### 离线构建

```text
data/raw/ 中的 PDF
  → PDF 解析（保留来源、页码、标题、章节）
  → Semantic 分块
  → MiniLM 向量化（CPU，384 维）
  → 保存 FAISS 索引和 chunks JSON
```

入口为 `build_semantic_index.py --version 版本名`：在独立目录构建并校验索引/JSON，发布后默认不改变当前选择，需 activate 或显式 --activate。`src/knowledge_base.py` 统一验证哈希、数量、维度及位置 ID，并原子切换版本；问答与评估共用读取入口。原始 Semantic 文件保留，无指针的旧项目仍兼容。新增固定 ID 论文清单下载入口，索引仍整体重建，尚无向量增量更新；`build_recursive_index.py` 保留为独立对照。双栏通过 `--two-column-files` 显式配置，五篇样本有抽查，尚未验证大量版式泛化。

### 在线问答

```text
main.py 加载已有 Semantic 索引
  → 用户问题 → API 判断是否需要分解
  → 原问题 Dense + BM25 检索
  → 可选 rewrite / HyDE 检索（默认关闭）
  → 原查询与可选检索列表做 RRF 融合
  → 若需分解：各子问题 Dense + BM25 + RRF，追加候选
  → 候选去重 → 原问题全局 BGE 重排 + 各子题局部 Top-3
  → 子题证据优先/首条保护，其余按全局顺序填充，最终最多 Top-10
  → 原文证据 + 规则化证据账本 + 必要的主体上下文
  → API 生成回答
  → 引用编号结构检查，必要时最多修复一次
  → 输出答案、引用来源和检查状态
```

分解判断在检索前进行；当前没有“根据检索结果发现缺口，再自主选择下一工具”的闭环。引用修复是格式处理，不是证据充分性或语义正确性的保证。

| 项目 | 当前设置 |
| --- | --- |
| 知识库 | Transformer、DCNN、VGG 三篇 PDF；378 Semantic chunks / vectors |
| Embedding | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`，CPU |
| 检索与重排 | FAISS Dense + BM25 + RRF；每路候选 60，RRF 保留 60；BGE CPU 全局重排并保留子题证据，最终 Top-10 |
| 生成模型 | 请求 `cn:deepseek-v4.1-flash`，反代返回 `deepseek-v4.1-flash`；标识不能独立证明上游权重身份 |
| 生成设置 | `thinking.type=disabled`、`temperature=0`、`max_tokens=4096` |
| 查询增强 | `USE_MULTI_QUERY=False`、`USE_HYDE=False`；rewrite 开关实际为原查询与改写查询融合 |
| 运行方式 | Python 3.11；本机反代 `http://127.0.0.1:7863/v1`；Embedding 与重排在本机运行 |

问题分解、启用的查询增强、回答和引用修复共用 API，不隐式回退到本地生成。Key 仅保存在忽略的 `api.local.json` 或环境变量 `RAG_API_KEY`，不写入日志、文档或 Git。运行命令见 [README](README.md) 与 [API 指南](docs/PYCHARM_API_GUIDE.md)。

### 2.1 数据与检索接口：不能丢失的技术事实

- 三篇论文共 32 页：Transformer 11 页、DCNN（AlexNet）7 页、VGG 14 页；不含 ResNet。解析产物约 86 个 Documents，与物理页数和最终 chunks 数是不同层级。
- Chunk 保留 `chunk_id/text/source/page/title/section`，`section` 可以为 `None`。当前 Embedding 和 BM25 都主要索引 `text`；保留 Metadata 不等于把 Metadata 编入检索文本。
- Semantic 构建实参为 `max_chunk_size=500, percentile=10`，长度单位是字符；函数默认 percentile=20 不等于构建参数。当前代码保留超过 500 字符的完整长句，不再像旧版按字符强切；仍会过滤很短的句子和片段，因此不保证无损。按 Document 独立处理，不能自动接回跨页断句。
- FAISS 为 `IndexFlatIP` 精确内积搜索，不是 HNSW/ANN 图索引；文档与查询均归一化后，内积对应余弦相似度。
- FAISS 向量位置必须与对应 chunks 列表一致；索引与 JSON 必须成对更新，数量相同也不保证语义对齐。历史片段编号不能跨分块版本直接复用。
- `RRF_K=60` 是秩平滑常数，`RRF_TOP_K=60` 是融合后返回数；每路候选数与最终 Top-10 又是不同参数。Cross-Encoder 只能重排收到的候选，不能找回已被截掉的片段。
- 当前 BM25 分词提取英文/数字词项；多语言 Embedding 不代表中文关键词检索已完善。批量评测应复用模型实例；当前 main 每次调用仍会重新初始化相关模型，不宣称已完成服务级缓存优化。

## 4. 已知缺口与开发约束

- 证据账本的主体归属、数值与限定条件处理是有限规则；引用结构通过不代表语义支撑通过。
- VGG 新题未检索到训练时固定 224×224 裁剪的证据，是检索覆盖问题；不能让模型用常识补成“有来源”的答案。
- Transformer 新题分解把联合机制拆成分别防泄漏的问题，可能引入错误前提，尚未修复。
- PDF 表格、公式、跨页句子和双栏解析仍有限。扩库先检查文本质量，再调整检索参数。
- 当前题目用于开发，没有独立盲测或总体准确率结论；服务发生过 HTTP 503，不能把服务错误当作知识不足。
- 清理后保留 `run_answer_evaluation.py`、`run_evaluation.py`、`check_evidence.py`、`metrics.py`。优先扩展必要入口，避免不断增加一次性诊断脚本。
- 保留函数式风格与必要中文注释。模块对外暴露少量清楚的操作，把重试、去重、证据映射等复杂度收在内部；出现真实替换需求时再抽象，不预先搭通用插件框架。
- 工作树已有大量修改、暂存和未跟踪内容；保留它们，不重置、不擅自提交或推送。Gold 和针对某题的答案替换规则不得进入生产流程。

## 5. 历史决策与后续路线（P0～P4 尚未实现）

### 历史诊断中应继续使用的方法

按 PDF 原文 → 解析文本 → 分块 → 初检候选 → RRF 截断 → 重排/上下文选择 → 生成/引用逐层定位问题，不因最终答案错误就只改提示词。

历史 q5 曾出现“候选池覆盖 4/4 必需结论，最终 Top-10 仅覆盖 2/4”的现象；这是旧实验的上下文选择诊断，不是当前新一轮测量。后续 Agent 应检查每个子问题的证据覆盖，必要时在相同上下文预算内比较子问题保留策略。旧 selector 原型已清理，不能描述成已集成能力；不同子问题的 reranker 分数也不能无条件直接比较。

历史 VGG 诊断还发现过关键证据被 RRF Top-20 截掉，以及提供 Gold-only 证据后小模型仍误读感受野。说明候选召回、上下文覆盖和生成理解需分别验证。Source Filter、Gold-only 和硬编码 ID 仅用于定位，不进入通用流程。

Parser V2 的深度布局/表格/公式开发曾明确延后，原型后已清理。扩库先做质量检查；只有多样题目证明解析是普遍瓶颈时，再单独规划解析改造，不因旧文档提及就自动恢复整套原型。

### Gold 与实验版本约定

现有 q1～q5 分别覆盖 VGG 小卷积核、位置编码、缩放点积、DCNN 数据增强、VGG/DCNN 比较；q6 为库外股价问题。q6 不参与检索均值，其拒答表现需看答案级记录。

`get_gold_chunk_ids` 按 source、page 和 NFKC/空白/大小写规范化后的 quote 子串匹配当前 chunks，结果去重。相同证据可能匹配多个重叠片段；现有 Gold/旧候选池不是穷尽相关性标注。Chunk Recall 与论断证据覆盖不同，扩库后应同时观察；改标注必须有原文依据并记录版本，不为提高分数而改 Gold。

每次对照固定并记录题集、Gold、索引/分块、查询分支、候选预算、RRF 参数、reranker、最终 K、上下文选择与生成设置。Original baseline 不得先经过 rewrite；相同辅助查询尽量复用。不要同时修改多个环节再把结果归因于其中一个。

历史版本规则：330、340、385 等数量和旧 MiniLM/BGE 表格仅用于回顾；默认三篇 Semantic 为 378，五篇先导版本为 1019，须按版本区分。Fixed 构建器、Parser V2、旧本地生成入口已移除，保留的旧数据不表示这些代码仍受支持。

### P0：批量导入与可复现知识库

第一批只接 arXiv，以 RAG / 检索 / 重排 / 自适应检索为主题。先用 5～10 篇覆盖不同版式的论文验证导入，再扩至筛选后的 30～50 篇；数量是起步范围，是否继续增加取决于题目覆盖和解析质量。

2026-10-19 首批五篇已完成固定版本下载、文件级幂等/失败重跑和独立构建；实测结果及尚未实现的通用导入能力见 [先导报告](docs/ARXIV_PILOT_2026-10-19.md)。以下为 P0 完整目标，不能把当前小批量入口视为全阶段完成。

流程：主题或论文 ID → 元数据候选 → 摘要筛选 → 正文获取 → 解析质量检查 → 分块与索引 → 导入报告。

保留论文 ID、版本、标题、作者、日期、URL、获取时间、内容哈希、可获得的许可信息，以及页码和稳定的文档/片段标识。区分发现成功、正文不可获取、下载失败、解析失败和入库成功；实现限速、有限重试、断点续跑及重复导入跳过。保留三篇旧库快照，再生成新库版本；初期小规模索引可以整体重建，不急于实现复杂的向量增量更新。

验收：同一批重复导入不产生重复文档；中断可恢复；抽查原文与片段顺序、页码、公式/表格；新旧库可分别运行，旧评测证据仍可定位。公开项目优先提供论文清单与下载脚本，全文再分发按各论文许可处理。

实习价值：展示数据接入、幂等处理、失败恢复、数据质量和证据溯源能力。

### P1：扩充评测并测量证据贡献

保留现有回归题，新增约 20～30 道有人工核对证据的起步题，覆盖单文档、跨论文比较、限定条件/数值、库内缺证据和版本差异。预先确定评分标准，划分开发集和留出集；调试不反复使用留出题。

另设明确标记的虚构文档评测组，用模型无法仅靠经典论文常识推出的新规则/数值测试证据利用。比较无上下文、正确上下文、无关/不足上下文、冲突上下文，分别统计事实正确性、来源忠实性、引用支撑和合理拒答；虚构结果与真实论文结果分别报告。

以同一知识库、题目、生成模型及一致的预算约束比较固定 RAG 与后续 Agent。保留 Top-5 历史表，同时补充与生产 Top-10 一致的检索评价；记录答案质量、工具调用数、token、延迟和失败。有可靠单价时再折算费用。

验收：每个评分点有原文依据；评估数据不注入生产提示；扩库后同时报告旧题退步与新题表现。检索/索引变化时重跑检索评测；只改最终措辞时优先固定证据回放。模型自评作为辅助，关键结论人工复核。

实习价值：能回答“提升来自哪里、对照是否公平、何时没有收益”。

### P2：完整的本地 Agentic RAG

复用现有检索函数，逐步形成：任务所需证据 → 初始计划 → 选择工具 → 观察结果 → 更新缺口 → 定向补充 → 综合回答 → 关键结论核对 → 停止。

首先提供本地混合检索、按文档筛选、读取相邻片段/页面；根据缺口选择改写、分解或 HyDE，而非所有问题默认全部开启。HyDE 文本仅用于检索，不能充当论文证据。

状态至少记录原问题、所需证据、已找到证据、缺口/冲突、行动记录、预算和停止原因。工具结果包含来源、页码/定位、内容及失败状态；日志保存简短的行动理由与结果，不要求模型输出冗长内心推理。

停止条件包括证据充分、部分可答、资料不足、连续行动无新增有效证据、预算用尽和服务失败。需要检查实体、数值与条件绑定、冲突来源及关键结论引用，不能只用模型一句“充分”判定成功。

验收：覆盖首轮足够、真实漏检、跨文档、错误前提、资料不足、来源冲突和 API 错误；缺口驱动的行动确实补到证据，或给出有依据的停止说明。不能硬编码已知 chunk ID 或题目答案。与固定 RAG 对照质量和成本，不预设 Agent 必然更好。

实习价值：展示状态管理、工具调用、证据反馈、异常处理与可解释的控制流程。

### P3：按需联网搜索与正文读取

在本地闭环可验证后接入。优先复用 arXiv 发现/读取能力作为论文搜索工具，再按实际任务需要选择通用网页搜索提供方。论文 API 查询与通用互联网搜索是不同能力，后者可能另有费用。

触发条件：用户要求最新资料、知识库时间范围不覆盖问题，或定向本地检索仍缺关键证据。区分搜索摘要和已读取正文；详细结论引用实际获取的内容。联网证据先进入当前任务，满足入库规则后才进入长期知识库。

验收：记录 URL、日期、获取时间和原文定位；正文不可访问时不伪称已读；外部文本只作为资料，不能改变系统指令；超时、限流和预算耗尽有明确状态。对同一组需外部证据的问题比较本地与联网模式，报告质量增益、额外延迟及调用成本。

### P4：编排、演示与实习材料

本地状态和分支稳定后用 LangGraph 表达已验证的流程，保持工具接口简洁，避免为迁移框架重写检索算法。补充简洁界面，展示回答、来源、证据缺口、行动过程、停止原因和耗时；整理依赖及启动说明，验证可复现启动路径。

最终交付：可运行 demo、架构与数据流说明、固定 RAG / Agent 对照表、两至三个失败复盘、核心代码讲解、真实贡献清单和简历草稿。按具体 JD 再决定是否需要 HTTP 服务或 Docker，不提前扩展分布式系统。

面试必须能解释：Dense 与 BM25 为什么互补；RRF 与 reranker 各做什么；rewrite/HyDE 何时无收益；为何模型换强后仍需要证据评测；Agent 什么时候应停止；扩库和联网引入哪些质量与成本问题。
